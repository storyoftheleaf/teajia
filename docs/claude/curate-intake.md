# Curate import, analysis and arrivals

> Moved verbatim from CLAUDE.md on 2026-11-03 so it loads only when needed. The short rules stay in [CLAUDE.md](../../CLAUDE.md).

## An import that cannot be read, and a quantity that has nowhere to go

**The analysis request is built against the model it is sent to, in [worker/src/curateAnalysisProvider.ts](../../worker/src/curateAnalysisProvider.ts).** Commit `4fb95152` (2026-07-20) added structured outputs (`output_config.format`) and, in the same diff, moved the default analysis model from `claude-sonnet-5` to `claude-sonnet-4-6`, which does not accept them. From that commit to 2026-10-17 every `intake_analyze` was refused with `invalid_request_error`, surfaced as `analysis_provider_400` and shown to Adrian as "We couldn't analyze this record". A two-line pasted invoice failed exactly like a fifty-page one, which is the tell: the record was never read. Putting the model back alone would have traded that 400 for another, because the Claude 5 family removed `temperature`. So both facts live in one capability table, read when the body is assembled; an unrecognised model is sent neither parameter and asked for JSON in words instead.

- **A refusal says which part of the request was wrong.** `analysis_error` now carries the provider's own `type` and `message`, sanitised (nothing key-shaped, one line, bounded), after the code. The code still leads because the browser matches on the `analysis_provider_` prefix to decide a draft is retryable.
- **A failed draft is not a dead end.** It used to have no items and no vendor groups, so `intake_update_item` had nothing to edit, `intake_set_group_vendor` nothing to assign, and `intake_finalize` previewed zero items. `intake_add_items` (and `POST /api/curate/imports/:id/manual-items`) adds hand-entered teas AND creates the vendor group they belong to — the one thing only analysis could do — reading them through the same `canonicalStoredItem` the analysis path uses, so a hand-built item finalizes through exactly the code a read one does.
- **A tea entered directly can carry what was bought.** `bought` on `curate_add_tea` / `curate_update_tea` takes a quantity (`g`, `kg`, `jin`, `piece`, `can`, `cake`) and a state (`ordered`, `in_transit`, `received`). Ordered and on the way wait as a pending arrival for `curate_approve_arrival`; received goes into stock through the same service that approval calls, so both doors leave the same product, receipt and ledger row. The reading is one function, [worker/src/curateAcquisition.ts](../../worker/src/curateAcquisition.ts), shared by both doors.
- **A cake is not a weight until somebody says what one weighs.** A tea counted in pieces, cans or cakes without `pack_size_grams` is refused by name rather than converted at an assumed weight. Teaware counts in pieces and is never weighed.
- **Sample grams stay separate and unknown.** `bought` is shop stock and will not take `purpose: sample`; a sample uses `sample_state`, and `sample_grams` only once it has been weighed (`grams_known = 0` is how "nobody has weighed it" is stored, and the holdings reading returns null for it). No received sample is ever defaulted to 5 g or 10 g.
- **Ordered and on the way are different facts, so the arrival says which.** Migration `0044` adds `curate_receipt_proposals.acquisition_state`, schema only, no default: NULL is the honest answer for the order rows written before the column existed.
- **An arrival can come OFF the list without going into stock, and only while it is pending.** Correcting a tea left its duplicate arrival sitting on the incoming shelf with nothing able to remove it: `curate_correct` answers "Unsupported Curate entity" for an arrival and `curate_undo` deliberately preserves them, so the only reject was the admin screen. `curate_reject_arrival` in [worker/src/mcpTools/curateArrivals.ts](../../worker/src/mcpTools/curateArrivals.ts) is that screen's reject through the agent door, under the same two steps and the same `curate_manage` gate every Curate correction uses. It marks the row `rejected`, the third value `status` has carried since migration `0000`, and KEEPS it: a DELETE would take the evidence with it, and `stock_ledger.receipt_proposal_id` points back here. **An accepted arrival is refused by name**, because its grams are on the shelf and a status flip would say the shop never received a tea it is selling; the answer there is `remove_stock`. The write goes through `prepareCurateRecordedWrite` with `arrival` registered as a recorded Curate entity, so the removal is attributable in `curate_history` and `curate_undo` puts the arrival back on the list rather than the rejection being a one-way door. An arrival whose linked order or tea can no longer be READ is still rejectable: that is the row most likely to need it, so the preview tolerates a failed details read instead of refusing on it.
- Enforced by [worker/tests/curate-analysis-request-shape.test.ts](../../worker/tests/curate-analysis-request-shape.test.ts) (the model gate, the sanitised detail, and a scan that fails if a second place assembles the request or names its own model), [worker/tests/a-failed-draft-is-not-a-dead-end.test.ts](../../worker/tests/a-failed-draft-is-not-a-dead-end.test.ts) (a 400 through to a finalized hand-built lot, driven through the MCP server against the migration ledger) and [worker/tests/a-bought-tea-waits-as-an-arrival.test.ts](../../worker/tests/a-bought-tea-waits-as-an-arrival.test.ts) (quantity to arrival to approval to stock, with the acceptance service reached through the worker's own route). The rejection side is [worker/tests/mcp-curate-arrivals.test.ts](../../worker/tests/mcp-curate-arrivals.test.ts), which drives it against the migration ledger: an accepted arrival's refusal is asserted through the authenticated `/mcp` route against real stock, so it fails if a rejection ever reaches the shelf.
