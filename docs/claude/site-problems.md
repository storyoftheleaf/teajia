# Site problems go to the builder, not onto the page

> Moved verbatim from CLAUDE.md on 2026-11-03 so it loads only when needed. The short rules stay in [CLAUDE.md](../../CLAUDE.md).

## Site problems go to the builder, not onto the page
**A visitor never sees a builder's problem.** Server errors, failed requests and stale rates land in `incident_ledger`; the platform owner reads them on **Needs fixing** at `/account/fixes` ([src/pages/SiteFixesPage.tsx](../../src/pages/SiteFixesPage.tsx)), linked from Your Table with a count when any were seen in the last 14 days. While any are, the person glyph that opens Your Table (bottom bar and desktop rail) is terracotta (`text-tea-error`) instead of its usual colour, for the owner only; gold stays reserved for "open". `useSiteProblemCount` in [src/lib/useSiteIncidents.ts](../../src/lib/useSiteIncidents.ts) is the one read. Each row is in plain words ([src/lib/incidentWords.ts](../../src/lib/incidentWords.ts)), with Mark fixed; rows quiet for 14 days fold away behind Clear all quiet.

- **Connection notices wait.** The offline bar (`NetworkStatus`) appears only after 8 seconds offline, and "Back online" only follows a bar that was shown. The request-failed pill (`NetworkErrorNotice`) waits 4 seconds and stands down if a request succeeds meanwhile. Wifi flickers used to flash both.
- **The site's own bookkeeping is not recovery.** Filing an incident or reading the ledger (`reportIncident: false`) never fires `NETWORK_RECOVERED_EVENT`; when it did, every slow request's notice was cancelled by the report about it.
- **The agent fixes a problem and then marks it, never the other way round** (Adrian, 2026-10-08: "I shouldn't mark them fixed. You should fix them and when they are fixed you mark them yourself"). Resolve a row only once the fix is live, with `resolution_ref` naming the commit or PR. Clearing rows as merely quiet is not fixing them.
- **A page that loses its files to a deploy reloads into the new build** instead of showing "Something went wrong": the root `ErrorBoundary` asks `reloadIntoNewerBuild` in [src/lib/versionCheck.ts](../../src/lib/versionCheck.ts), which shares the version check's 30-second cooldown so it cannot loop. Enforced by `tests/stale-build-reload.spec.ts`.
- **A new server-side health check uses the same pair**: `recordHealthProblem` when it fails, `clearHealthProblem` when it passes, one fixed signature, so it shows on Needs fixing and clears itself.
- **A new serious problem is handed to i64os, never texted to the owner.** [worker/src/problemAlerts.ts](../../worker/src/problemAlerts.ts) (`handoffToRepair`) is called after `upsertIncident` in `handleCreateIncident` and after `recordHealthProblem` in the cron. Only when the row is new or was resolved and came back (`{ row, change }`; a repeat of an open row is silent) and only severity `high` or `critical`; wifi drops and timeouts are `medium` and stay out. It POSTs `{ source, repo, incident: { ..., sentence, change } }` to `https://app.i64os.com/api/v1/repairs/incident` with header `x-i64os-repair-secret: $I64OS_REPAIR_SECRET`, 5s timeout, never throws, never logs the secret, and records each handoff in `problem_alerts` (kind `handoff`, migration `0033`). No secret, no handoff. **The worker sends the owner no message of its own**: i64os has Claude Code fix the problem and open a pull request, and sends the one morning Telegram message in which the owner merges with one tap. Nothing merges without that tap. **The same secret is the contract in the other direction**: i64os presents it as `x-teajia-repair-secret` and may call exactly two routes with it, `GET /api/platform/incidents` (read open problems) and `PATCH /api/platform/incidents/:id` (statuses `repairing`, `open`, `resolved` only), compared in constant time by `hasRepairCredential` in `worker/src/index.ts`. Every other route refuses it. The `resolution_ref` i64os writes is one of `fix ready: <PR url>` (status open, a passing PR awaits the tap), `fixed: <PR url>` (resolved after the merge) or `auto-repair stopped: <why>` (open). Enforced by [worker/tests/problem-alerts.test.ts](../../worker/tests/problem-alerts.test.ts), which also fails if the worker grows a Telegram call again.
