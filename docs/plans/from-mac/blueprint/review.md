# Independent review of the integrated blueprint

**17 November 2026. Disposition: accept the map and bounded delivery order; require the editorial contract corrections below before implementing the incoming-issue pilot.** This is an independent product/engineering review of the assembled plan, not authorization to build, migrate, publish or delete. I inspected the working plan, blueprint chapters, route crosswalk, and targeted implementation/schema/tests at checkout `4f884507` with local edits. I did not repeat the live observations or run a new acceptance suite. Production receipt claims remain evidence cited by the plan, not independently reproduced here.

The plan's strongest decision is to keep the existing operating spine and several editorial paths visible rather than replace them with a new universal application. Its largest remaining weakness is that “approved edition” is still a product phrase where the implementation needs a precise immutable object and an atomic approval rule. More screens will not resolve that seam.

## 1. Approval must bind the exact revision, across every publishing door

**Required prerequisite for K1; highest consequence.** The plan correctly identifies that a new Wordforge revision overwrites the article and resets it to draft. Preserving an old live snapshot alone would still leave a second race: approval currently names an article, not the reviewed content.

The MCP publication preview creates a ticket containing account, article ID, target state and date, then confirmation updates that article without a revision comparison. REST publication likewise selects ID/date and publishes the current row. Therefore an editor can review revision A, a sync or another editor can replace it with B, and confirmation can publish unseen B. The browser persistence queue serializes one editor's calls; it cannot serialize another browser, sender or MCP client. REST update also accepts `status` directly, so repairing only the dedicated publish handler leaves another publication door. [MCP preview and commit](../../worker/src/mcpTools/writing.ts#L580) · [REST update and publication](../../worker/src/index.ts#L24168) · [Browser queue](../../src/admin/articlePersistence.ts#L23) · [Sync replacement](../../worker/src/wordforgeArticleDraft.ts#L182)

**Disposition:** Make “publish/replace the exact reviewed revision” a single server invariant used by REST, MCP and issue placement. A stale review must refuse without changing live bytes. Keep the previous approved revision and stable address live while a replacement is pending. Include native D1 editing: its autosave also mutates a public row. Do not simply exempt imported fields from the 409 or add a Publish button. The acceptance fixture must interleave preview A → sync B → confirm A, then prove explicit approval of B works. This is a requirement on the slice, not a prescription for a large editorial backend.

## 2. Source family, output identity, article address and issue placement are four different things

**Resolve before choosing the real keeper or writing the adapter.** The source register usefully distinguishes the An Cha trilogy, AR Create audience editions, the vault issue and Teajia placement. The receiver does not yet express those distinctions: one `(account, source_system, source_id)` maps to one article, with one revision counter. Reusing an interview/project ID for three articles would replace the same destination three times. Adding a fresh source ID for every revision would instead defeat retry identity and create duplicates. The correct mapping must be chosen deliberately. [Source register](source-register.md#smallest-coherent-editorial-delivery) · [Source schema](../../worker/migrations/0000_initial_schema.sql#L93) · [Unique mappings](../../worker/migrations/0000_initial_schema.sql#L1936) · [Receiver lookup](../../worker/src/wordforgeArticleDraft.ts#L174)

There is also a public-address decision hidden in the adapter: each sync rewrites `slug`, but public lookup uses only slug and the database has a global unique slug index. Account-scoped private authorship does not imply account-scoped public URLs. A rename can strand an existing link; two shops cannot independently claim the same slug. The public list currently aggregates published articles across accounts. Thus wiring that list into Read is also a cross-store editorial inclusion decision, not merely fixing an unused fetch. [Sync fields](../../worker/src/wordforgeArticleDraft.ts#L193) · [Global slug uniqueness](../../worker/migrations/0000_initial_schema.sql#L1960) · [Public list and lookup](../../worker/src/index.ts#L24299)

**Disposition:** For the pilot, define one stable external output key, parent source-family reference, reviewed revision, stable public address, destination account and explicit issue slot. Keep the private vault issue as editorial intent and Teajia placement as public delivery authority unless Adrian deliberately chooses otherwise. No shared registry migration is needed to prove this. Use fixtures with two outputs from one family, duplicate slugs, a renamed title and an unplaced published article; none should silently replace or enter another issue.

## 3. The import contract needs integrity and authority checks, not just template repair

**Required inside the same K1 slice.** The blueprint correctly catches `immersive` versus `immersive_scroll`, unsupported blocks, discarded article-level credits and protected-field editor conflicts. Those are real source-backed findings. Two additional seams matter:

- Revision comparison happens before the write batch. The update has no expected-revision predicate, so sequential stale-input tests do not prove safety against overlapping newer syncs. The supplied hash is checked for shape, not recomputed from a canonical payload in this receiver. Treat it as a sender assertion until the trust contract says otherwise. [Decoder/upsert](../../worker/src/wordforgeArticleDraft.ts#L142) · [Sequential receiver tests](../../worker/tests/wordforge-article-draft.test.ts#L92)
- Normal REST author/subject writes call account-aware contributor validation. The integration decodes string IDs and calls its upsert directly. A valid integration token fixes the destination account but does not itself establish that the referenced contributor is associated with that account. The server must either resolve/validate the references or explicitly require a trusted mapping with tested refusal. [Integration handler and contributor validator](../../worker/src/index.ts#L24021)

**Disposition:** Require atomic monotonic revision acceptance and explicit contributor/media/credit validation at the import boundary. Test overlapping revisions, identical retry, same revision with conflicting content, missing or foreign contributors, and every accepted block through the actual chosen reader. A template name change without these checks is not completion. The current tests demonstrate sequential behavior, not these additional cases; the concurrency failure is a code-derived risk, not a reproduced production incident.

## 4. “Same tea” must mean linked records, not one record everywhere

**Clarify the M1→M3/K3 proof; do not broaden into a canonical-tea migration.** The blueprint's identity columns mostly get this right. The working plan's shorthand “one canonical tea” can still be read as requiring a single global tea object. Existing contracts deliberately separate encounter, product, sample portion, purchase/receipt and personal memory. A product links back to the encounter; a purchased buyer entry or share claim can be a distinct personal record with source provenance. Reusing one ID across these boundaries would destroy ownership or quantities. [Consumer identities and quantity rules](../../docs/CURATE_CONSUMER_CONTRACT.md#identities-and-quantities) · [Buyer entry insertion](../../worker/src/index.ts#L6656) · [Share claim destination](../../worker/src/index.ts#L18488) · [Journal confirmation](../../src/pages/ShareCardPage.tsx#L70)

**Disposition:** The operating proof should record an explicit ID/ownership ledger: account, encounter, product, purchase line, receipt/movement, inquiry, invoice/payment, buyer identity and resulting personal record. Assert links and accounting conservation, not universal ID equality. Keep sample consumption independent of saleable stock. Before any P1 label or destination repair, prove where a claim persists and whether Journal actually reads it under the recipient's personal account; retry and account-switch tests must assert the destination record as well as the success message. A public Wisdom/Craft relation should use a reviewed reference and eligible product projection, never copy private supplier evidence to make the chain look complete.

M4 publication parity is a prerequisite to the first controlled public sale, not a later polishing task. “Counted stock” also must not be silently rewritten as “positive stock”: the shared readiness helper accepts a known zero, and sold-out addresses have their own retention policy. Carry the approved distinction through server and MCP paths. [Publication requirements](../../src/lib/productPublication.ts#L15) · [Working queue M3/M4](../../WORKING_PLAN.md#delivery-queue)

## 5. Withdrawal and cleanup need resource-specific outcomes

**Keep the consolidation restraint; tighten the promise.** The plan correctly keeps private originals, migration history, legacy fixtures and current design references. There is no basis for mass deletion from duplicate counts or absent local Photos directories. Those are inventory observations, not proof that a source or consumer does not exist. [Consolidation prerequisites](consolidation.md#reviewable-file-decisions) · [Source holdings](source-register.md)

The K1 wording that withdrawal removes “public contents and delivery” needs an explicit resource scope. Curated JavaScript is authorization-checked per request and fail-closed. Static photos, public metadata, earlier deployed hosts and copies already downloaded have different lifecycles. D1 status removal, curated route visibility and publication of a prose overlay are also separate controls. Do not claim revocation merely because the Read card disappeared, and do not delete shared media as the default withdrawal operation. [Protected module delivery](../../functions/readAssetDelivery.ts#L1) · [Editorial delivery distinctions](editorial.md#templates-readers-and-delivery)

**Disposition:** Specify expected post-withdrawal behavior for issue entry, direct route, article API, module bytes, social metadata and media URLs. Keep media removal/retention explicit and dependency-aware. Verify anonymous and authorized requests, dependency failure and supported old deployment hosts on the exact candidate. Already downloaded copies cannot be recalled. Move no sources or active migration inputs until the listed replay/reference proofs exist.

## Dependency adjudication and smallest demonstrable delivery

The correct order is two bounded lanes, not one grand rebuild:

1. **Operating lane:** repair the existing source CI gate; preserve current Curate; prove M1 physical receipt and retry; enforce M4 publication parity before M3's public sale; then complete that same order through payment, movement, fulfillment and buyer view. Use controlled refund/cancellation fixtures and real operating evidence separately. Event billing and second-store expansion do not belong inside this slice.
2. **Editorial lane:** settle the output/revision/address/placement contract above; import one synthetic item through the existing receiver; open it in the actual editor and renderer; deliberately place and publish it; ingest a second revision while the first remains live; reject stale approval; explicitly replace; withdraw and verify delivery. Only then use a real keeper and its permissions. AR Create transport expansion, trilogy/series UI, generalized issue administration and new reader templates are deferred until this slice proves the contract.

A demonstration using an already published Porcelain route is useful for placement and regression, but cannot establish the incoming D1 revision workflow. Conversely, a synthetic D1 import does not validate subject approval, original photography or the vault's published edition. Keep those evidence claims separate. No business-data correction, new public navigation or release is authorized by accepting this review.
