# K-A editorial revision contract

Evidence baseline is Teajia `94dc1a5ed71dbb53ef779a90208d233309f21843`. This is the contract and fixture boundary for [K-A](BUILD_LIST.md), based on the [editorial inventory](editorial.md), [source register](source-register.md) and [independent review](review.md). The failures below are predictions from the pinned code unless a test is explicitly cited. This planning pass made no product, data or release changes.

## Identity and ownership

| Object | Minimum contract |
| --- | --- |
| Source family | Opaque private provenance that groups related outputs. Vault Magazine retains the original material, source grades, quote checks, rights and issue intent. AR Create retains its Article Piece and chosen audience edition. WordForge retains its compiled input and delivery receipt. A family can yield several articles. Record the family association privately in Teajia for the pilot, using a seeded association for synthetic v1 inputs. The strict v1 payload has no family field. Keep that envelope compatible and defer any sender-side family mapping contract to K-E. |
| External output and destination | `(destination account, source system, stable output key)` identifies one Teajia article ID. For current WordForge v1, `source.id` and the route `:sourceId` must match and identify an individual WordForge Article output, so parts 1 and 2 use distinct IDs and share a separate family association. A retry or preferred title never allocates a new output. The bearer fixes the destination account server-side. Native and event drafts use Teajia article IDs, with the existing account + event seed identity retained. |
| Sender revision and Teajia revision | The sender's positive monotonic revision orders deliveries within a single output. The receiver verifies its server-recomputed SHA-256 and records the sender revision and digest in the private receipt. Each accepted import or effective local edit creates a separate immutable Teajia candidate revision with its own digest. Teajia approval always identifies that candidate. A new upstream revision with identical presentation still advances the candidate when accepted, so its provenance receives review too. |
| Article fields | For WordForge, source owns manuscript title/subtitle, tags/category, ordered blocks including cover and other media suggestions, and submitted credit/attribution suggestions. Teajia owns the address, accepted contributor/subject/attribution assignments, approved cover override, presentation/layout and reading-time choices, clearance, and issue placement. Keep source values and Teajia overrides distinct, even when the wire fields overlap. Native drafts use Teajia-owned editorial fields throughout. Explicit accepted overrides carry forward to the next effective draft, where they are reviewed again. Failed or conflicting saves leave the last accepted candidate intact. |
| Public address | Retain `/article/:slug` for D1 and the existing `/read/…` routes for bespoke stories. Claim the globally unique D1 slug transactionally on first creation with a useful conflict response. Preserve the assigned slug once public, through title changes, retries, source renames and withdrawal. A changed upstream slug can be shown as a suggestion. Address moves and redirects are outside this cut. |
| Issue placement | Teajia owns delivery. A slot has a stable key `(issue account, issue ID, slot key)` and an explicit approved article + revision, with rank/feature membership in the placement decision. The pilot uses one seeded issue/slot and requires the platform Magazine authority plus same-account article ownership. Publish without a placement can preserve the direct-address behavior of the existing catalogue. An unplaced public article never joins Read automatically. Replacing a placed edition includes its current approved slot in the review and changes both pointers atomically. Refuse a conflicting occupancy, cross-account article or stale slot version. |

**Import integrity.** Reproduce the current sender's v1 digest over UTF-8 canonical JSON of `{schema_version:1, source:{system,id}, article}`, excluding revision and the supplied digest. Sort object keys recursively by string order, preserve array order and JSON values, and use ordinary JSON string/number serialization. The canonical fixture at the Teajia baseline reproduced its supplied digest with this algorithm. Compare after exact shape validation and before presentation mapping. Same latest revision and verified digest returns the same article and revision receipt without writes. Same revision with a different digest and any lower revision return a conflict. A higher revision advances the source receipt and candidate together. Re-read a losing insert/update to classify a retry or conflict. Authenticate the destination and validate contributor associations using the same stewarded/associated rule as native REST. Restrict pilot media to verified, account-owned immutable objects or an explicit reviewed fixture allowlist. Reject foreign media, mutable keys, unknown objects and unapproved external references. Check every media-bearing field and preserve both article-level credits and block-level credits. The receiver's cover/layout normalization and fidelity proof belong in K-B. ## Approval and atomicity

1. The server issues an immutable candidate ID and digest over the versioned editorial projection the review actually displays. The projection includes title/dek, ordered content and its layout, printable names/credits, approved media identifiers and alt/caption/crop, article metadata and its stable public address. Pin media by an immutable key or digest. An approved link may still follow normal current access, published-profile and product-eligibility rules. Changes to dependent account/catalogue records follow those records' own authorization. Linked product IDs selected by the editor are part of the approved edition wherever they feed the story's public relations.
2. A review identifies the account, target, candidate ID/digest, expected current draft head, expected public generation and the explicit placement operation plus expected slot generation when required. The UI uses the candidate returned for the exact content shown in the review. It displays approval only after the relevant save returns and the preview reflects that revision. MCP uses the existing single-use ticket with those bindings and an exact revision review link or payload, alongside its textual preview. Share the same publish/replace function across the REST action, MCP confirmation and the placement action. Keep the existing fresh session and account authority checks. The approval receipt records actor, target, candidate/digest, previous public revision, approval time and placement effect. Source clearance stays distinct from this Teajia approval.
3. Commit publication using a conditional write or guarded D1 batch. At commit, verify draft head, public generation, selected revision ownership, contributor/media authority and any issue slot expectation. The live projection, public revision, placement effect and durable receipt advance together. Compare at the write and ensure every other write in the transaction depends on the winning guard. A zero-row guard cannot leave partial changes. Unique constraints resolve first-create and global slug races. In WordForge, include the expected source revision and editor head in the write boundary. A retry may rebase an unchanged source delivery on the current editor-owned fields, or return a conflict if that merge is ambiguous. It cannot lose accepted editor edits.
4. Return `409` for stale review or write conflict and require a new review, even if the stale candidate still exists. A browse/save operation never chooses the next public revision. A retry of the same successful approval may return its existing receipt and performs no write. Public generations advance even through withdrawal and re-publication so a stale approval cannot become valid again. Withdraw/archival targets the expected current public generation and clears public eligibility and any active slot atomically while retaining history and the address. Preserve the first `published_at` and record replacement times separately. K-C verifies the complete withdrawal delivery boundary.
5. REST draft updates reject direct `status` and `published_at` writes and require the expected draft base for a content edit. MCP draft-edit tickets carry the corresponding base revision. Creates and event seeds remain draft-only. Separate the draft head from public state in the editor response and retain legacy public projections during rollout. Avoid deriving correctness from a browser queue, edit timestamps, a disabled control, or the ticket age.

## First fixture and implementation cut

The first independent work can add one failing Worker integration fixture using the existing signed receiver, `SqliteD1`, a test account with a Publish-authorized human, and the exact v1 fixture. Own the test file only while platform route and persistence ownership are arranged. Start with a WordForge sandbox A already live, then repeat the D1 race through native autosave. Assert the approved public list/detail body, address and publication date. Take a new review of A, then use the WordForge sender or a second signed editor to stage B, assert that the public projection is still A, attempt the already-issued A approval through REST and MCP, and assert a stale refusal. Explicitly review B and verify the same address now serves B. An unplaced published control article stays outside the issue. The existing tests cover sequential receiver behavior. [Receiver fixtures](https://github.com/storyoftheleaf/teajia/blob/94dc1a5ed71dbb53ef779a90208d233309f21843/worker/tests/wordforge-article-draft.test.ts#L83)

| Synthetic failure or race | Required assertion |
| --- | --- |
| Two outputs from one family, title rename and second tenant slug collision | Two article IDs and stable output receipts. Rename leaves the live address fixed. Other tenant with the same desired slug gets a conflict with no source row, candidate or issue side effect. |
| Concurrent syncs B and C both observe A, then C commits first | Interpose a deterministic barrier before the actual write and release C before B. B refuses. Stored source revision, digest and candidate belong to C. Both first-write retries and same-key different-content races yield one creation/winner and no orphan. A same-revision changed payload with the original claimed digest fails verification. |
| Reader has A, editor reviews A, then B lands | Drive B through both external sync and native autosave in separate cases. A remains byte-for-byte in the article-controlled public projection and active slot. Stale REST, MCP and placement attempts refuse. B appears only after explicit B approval. Also force approval to win just before B in a second interleaving, where A remains the approved revision and B stays pending. |
| Editor patch and sync cross | A cover/attribution override and incoming manuscript never overwrite each other silently. Successful merge yields a fresh composed candidate with both choices and leaves A live. An incompatible or stale patch returns a conflict. |
| Wrong account/authority and wrong resources | Integration header/body cannot change the configured destination. Foreign/unknown contributor IDs, foreign/non-immutable media, wrong-account editor/placement and wrong issue occupant produce no changes to the public row, draft, or accepted receipt. A separately associated, eligible contributor succeeds. |
| Bypasses, withdrawal and retry | Direct status/date updates refuse. Fresh draft edits, overlay save, legacy photo write and restore never promote live content. A stale public-generation withdrawal cannot hide a newer edition. A repeat of successful approval returns the recorded receipt; inject a write failure and assert projection, placement and receipt have rolled back together. Existing public xref membership changes only on approved replacement for the governed story. |

**Storage and rollout.** Add durable schema before the authorized real pilot. Reuse `articles` as stable identity and public projection, with an account-scoped immutable editorial revision store and draft/public head state. A first-time draft can keep a draft-only identity row for existing foreign keys. After first publication, write draft content into the revision store and replace the existing public projection only on approval. Use the existing external-source mapping and add the minimum private family/receipt fields and one durable placement relation. The head tracks a monotonically increasing public generation. Keep exact prior authored bytes or an equivalent immutable public projection. For an existing live row, that row already serves A while B is pending. Capture A lazily as a legacy snapshot inside the first governed transition that would destroy or withdraw that public state, before replacing it. Label it as legacy live evidence and leave historical approver claims empty. Likewise preserve an existing curated published overlay on first governed transition and bind its released base identity. No bulk data backfill or old-site byte crawl is required for the synthetic cut or compatibility rollout. The proof compares the article-controlled projection under fixed dependencies. Dynamic catalogue/profile eligibility, published resources and immutable Pages host byte evidence have their own verification. A data-changing migration, if later chosen, requires the repository's seeded before/after review page before push. Implementation requires authorization and one persistence owner with coordinated platform Worker/index ownership, plus Read/edge ownership for the bespoke controls.
