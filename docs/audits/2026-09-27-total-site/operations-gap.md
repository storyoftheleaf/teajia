# Operator workflow gap pass — 2026-09-27

Source baseline: `2a096303`. This bounded, read-only pass traced one failure path each in intake/Curate, customer save, and receipt movement. It did not run a browser, server, tests, or production requests. These are source-confirmed failure sequences, with runtime reproduction still needed before describing them as observed incidents. The findings do not overlap the business and security reports in this directory.

| **OPS-01 — Intake can silently lose the purchase record** | **P1 / high source confidence** | With “Save purchase record” on and a staged vendor group with cost or order data, product chunks are created first ([`IntakeWorkspace.tsx:354`](../../../src/admin/views/IntakeWorkspace.tsx)); each purchase-order failure is converted to `null` ([line 381–394](../../../src/admin/views/IntakeWorkspace.tsx)); the page still shows success, attempts to abandon its server draft, clears local staging, and navigates away (lines 397–406). Reproduce by allowing `/api/products/bulk` and rejecting `/api/purchase-orders`. The products exist, but the requested purchase record does not, and the operator gets no failure signal or retained staging to repair it. | Report the partial outcome distinctly, retain the staged/vendor purchase data for retry, and only close the draft once requested records are saved or explicitly skipped. Size: small–medium. |
| **OPS-02 — Retrying a failed contact save can create a duplicate** | **P2 / high source confidence** | New-contact save calls `POST /api/customers`, then a separate relationships `PUT` ([`CustomersView.tsx:1454`](../../../src/admin/components/CustomersView.tsx)). If the POST succeeds but the PUT fails, the catch says “Could not save contact” and leaves the form open (lines 1461–1469). The next Save performs another POST. The Worker assigns a fresh random ID per POST ([`index.ts:8709`](../../../worker/src/index.ts)); the schema has no uniqueness constraint on contact identity, only ID ([`schema.sql:170`](../../../worker/schema.sql)). The POST already writes the requested relationships ([`index.ts:8736`](../../../worker/src/index.ts)), so the second request is redundant on create. Reproduce by succeeding the POST, failing only the relationships PUT, then clicking Save again. | Remove the redundant relationships PUT when the customer payload already includes those kinds; make the create response the commit point and retry later relationship edits against the returned ID. Size: small. |
| **OPS-03 — Manual retry can double-receive a partial stock delivery** | **P1 / high source confidence** | The receipt panel calls `receive(lineId, quantity)` with a new random key for each click ([`IncomingReceiptsPanel.tsx:54`](../../../src/admin/components/inventory/IncomingReceiptsPanel.tsx), [`api.ts:1565`](../../../src/lib/api.ts)). The Worker correctly deduplicates the *same* key ([`index.ts:14932`](../../../worker/src/index.ts)). If a 5-of-20 receipt commits but its response is lost after transport retries, the panel keeps the old line and shows an error; clicking Receive again sends the same 5 with a new key. It is valid against the remaining 15 and records another 5. The same stale retry is possible when the receive request succeeds but the subsequent list refresh fails: the panel merges `action()` and `load()` in one try/catch and retains old receipts ([`IncomingReceiptsPanel.tsx:12`](../../../src/admin/components/inventory/IncomingReceiptsPanel.tsx), [line 24–28](../../../src/admin/components/inventory/IncomingReceiptsPanel.tsx)). | Retain one idempotency key per pending receive intent until a server-confirmed result, and separate a successful write from a failed refresh. Disable another receive on stale data until reconciliation. Size: small–medium. |

Curate import creation holds a stable key while the panel is open ([`ImportPanel.tsx:213`](../../../src/components/TeaCompass/import/ImportPanel.tsx)); finalization uses a key derived from the batch ID ([line 343–349](../../../src/components/TeaCompass/import/ImportPanel.tsx)). The server replays completed finalizations and resumes same-key work with idempotent receipt and movement primitives ([`curateImportFinalize.ts:141`](../../../worker/src/curateImportFinalize.ts), lines 202–215). I did not find a duplicate-finalize gap in that path. This is targeted source coverage, not an end-to-end validation of every import disposition.
