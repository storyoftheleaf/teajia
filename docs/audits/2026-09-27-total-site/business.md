# Teajia business logic and admin integration audit

Source audit of `2a096303` on 2026-09-27. No production data, browser session, deployment, or migration was changed. Findings below are reproducible from current call paths; no claim about production data prevalence is made. Focused existing tests passed: `npx vitest run src/admin/hooks/useAdminData.test.ts worker/tests/shipping-rate.test.ts --testTimeout=20000` (11 files, 125 tests). Those tests do not cover the cases below.

## Findings

### BIZ-01 — Inherited freight and deliberate zero values are lost at the admin product boundary (P1, high confidence)

`GET /api/products` selects `p.*` and returns `addPricingFields` without replacing `shipping_rate_per_kg` or `fixed_retail_price_usd` (`worker/src/index.ts:2520-2554`). `useProducts` then maps `shipping_rate_per_kg: null` to `0`, `fixed_retail_price_usd: 0` to `null`, and a deliberate `low_stock_threshold: 0` to `100` (`src/admin/hooks/useAdminData.ts:49,65-66`). This is a direct value transformation; a raw `{shipping_rate_per_kg:null,fixed_retail_price_usd:0,low_stock_threshold:0}` becomes `{shippingRatePerKg:0,fixedRetailPriceUSD:null,lowStockThreshold:100}`. The freight cell consequently shows `$0` with the pinned dot (`InventoryRow.tsx:273-289`), Product Edit previews zero freight (`ProductEditPanel.tsx:1156-1166`), duplication carries a zero per-tea rate (`AddProductModal.tsx:411-418`), and the inventory CSV labels the tea as pinned (`InventoryView.tsx:1252-1255`). The actual Worker retail calculation still inherits the shop rate, so admin labels and pricing preview disagree with the shelf. An explicit free retail override is visually replaced by formula retail; a zero low-stock threshold displays as 100. Preserve nullable values with `p.shipping_rate_per_kg == null ? null : Number(...)`, and treat a zero override and threshold as entered values. **Size:** small, with focused adapter tests for `null` and `0`.

### BIZ-02 — Editing an order can replace its items with another order's items (P1, high confidence)

`OrdersView` keeps one mounted `EditOrderModal` instance (`OrdersView.tsx:1167-1172`). Its item-loading effect does not clear `items` or cancel/identify pending responses (`EditOrderModal.tsx:53-77`). Open A and load its lines, close it, then open B; if B's `getItems` fails, `fetching` becomes false while A's `items` remain. Save is enabled for that nonempty array (`EditOrderModal.tsx:307-319`) and sends the A lines to B (`EditOrderModal.tsx:107-127`). A late A response after B opens can cause the same result without a network failure. The Worker accepts replacement lines and deletes/reinserts all lines in one batch (`worker/src/index.ts:6259-6309`). Clear state before each load; discard responses unless they match the currently open invoice; keep save disabled after a load failure. **Size:** small/medium, with a two-invoice race and failure test.

### BIZ-03 — “Save + Share” can report invoice creation failure after it succeeded (P1, high confidence)

`QuickInvoiceModal.tsx:437` creates the invoice, then `:448` awaits PDF generation and native sharing inside the same `try`. If the browser share is canceled, PDF creation fails, or the download throws, `:454-455` says “Invoice creation failed” and leaves the populated modal open. A retry creates another invoice with a new number; the Worker create path has no client idempotency key (`worker/src/index.ts:5199-5275`). Separate the committed invoice result from the share/download step. Close or mark the invoice saved once create returns, and offer a retry for sharing that does not create again. **Size:** small/medium; test rejection after a successful create.

### BIZ-04 — Account switches can display prior-store orders and event data from shared query keys (P1, high confidence)

Both `ActivityView.tsx:29-36` and `PendingView.tsx:25-34` store account-owned pending invoices under the constant `['invoices-pending-summary']`. `usePendingAttendees` similarly uses `['pending-attendees']` (`src/admin/hooks/useEventData.ts:155-161`); `VendorProfileView` uses `['invoices-all']` (`:95-100`). `AccountSwitcher.tsx:75-80` invalidates all queries after the token changes, but invalidation retains previous data while refetching and after a failed refetch. `PendingView` renders that data under the newly selected account, exposing previous-store customer names/order IDs. The same keys are eligible for the 24-hour localStorage query persister (`src/index.tsx:24-27,43-68`), and logout only clears token/account state (`AdminApp.tsx:449-454`). Scope these keys by account and user and gate display on a token scoped to that account; exclude sensitive order/attendee data from persistence or clear it on logout. **Size:** medium, with a two-account switch and failed-refetch test.

### BIZ-05 — Product story crashes for any returned product (P2, high confidence)

The protected route `/admin/products/:id/story` is reachable from the Product Edit panel (`AdminApp.tsx:587`, `ProductEditPanel.tsx:1882`). `ProductStoryView.tsx:244-249` calls `api.products.list()` and casts the raw snake_case Worker rows to `Product[]` without mapping. The Worker returns `retail_price_per_gram_usd`, while the view calls `product.pricePerGramUSD.toFixed(3)` at `ProductStoryView.tsx:613`; that property is undefined, so rendering throws. Most other names, stock, cost, and images are also blank or zero. Reuse the same product adapter as `useProducts` and test the route with a realistic Worker row. **Size:** small/medium.

### BIZ-06 — Vendor profile shows false stock economics and unrelated “purchase history” (P2, high confidence)

`GET /api/customers/:id/products` returns only snake_case fields and omits `cost_per_gram_usd` (`worker/src/index.ts:9027-9040`). `VendorProfileView.tsx:88-119` treats these raw rows as camelCase `Product`: total cost, stock value, average cost, displayed stock, and names are therefore zero/blank even with real products. Its “Purchase history” fetches customer sales invoices and filters `customer_name` by vendor name (`VendorProfileView.tsx:95-127,293-330`), which cannot establish that this store purchased tea from that vendor and can show an unrelated sale on a name collision. Purchase orders have their own `vendor_id` and `vendor_name` (`worker/src/index.ts:20235-20262`). Use an explicit vendor product DTO or adapter and a vendor-keyed purchase-order/receipt read. **Size:** medium.

### BIZ-07 — A failed partner listing save becomes impossible to retry unchanged (P2, high confidence)

`PartnerListingEdit.tsx:434-467` advances `lastSaved.current` before awaiting `updateListing` for stock, price, sample availability, and note. `persist` catches the rejection and only shows an error (`:425-432`). Blurring the field or clicking the same sample choice again then returns immediately because the entered value equals `lastSaved`, although the Worker may have rejected it. Price changes can fail because the FX rate is unavailable (`worker/src/index.ts:24715-24725`). Set the saved snapshot only on a successful response; on failure retain the dirty state and offer an explicit retry. **Size:** small.

### BIZ-08 — Session-storage fallback cannot use several admin upload/token actions (P2, high confidence)

`setToken` deliberately falls back to `sessionStorage` when localStorage is blocked (`src/lib/api.ts:605-618`), and the shared authenticated fetch reads either store (`:596-597`). Flyer upload (`:2454-2465`), venue photo upload (`:2488-2497`), and the Voice & agent access page (`src/admin/views/MCPTokensView.tsx:52-58`) read only localStorage, so an otherwise authenticated fallback session sends no bearer token and gets 401 from the protected Worker routes (`worker/src/index.ts:12697-12700,12911-12914`). Use the shared token/header path for these calls. **Size:** small; test with localStorage writes blocked and token in sessionStorage.
