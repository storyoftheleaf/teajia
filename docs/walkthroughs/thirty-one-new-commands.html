Thirty-one new commands

Things you can now ask the shop to do out loud, on top of the fifty-three it already answered to. Say them however you like; the names underneath are only what the machine calls them.

None of these work until a session is connected. Mint an owner-tier token at /admin/mcp-tokens, set it as TEAJIA_MCP_TOKEN in the claude.ai/code environment, and add api.teajia.com to that environment's network allowlist. Both halves, or it fails at the proxy in a way that reads like a bad token and is not one.

How the ones marked “asks first” behave

It shows you before it does it

Anything that changes something answers twice. The first time it tells you what would happen and how many rows it touches. Only the second call commits it, and only with the token from that preview.

A confirmation cannot be spent twice

Nor handed to a different command, nor used by a different token, nor applied to a different shop. It commits exactly what the preview showed you, not whatever happens to match by then.

Ambiguity is refused, never guessed

Two teas matching what you said, two invoices in different currencies, a collection that would be emptied: all reported back rather than resolved on your behalf.

What was deliberately not built

  • Denying, waitlisting or cancelling an RSVP. The admin path also promotes the first waitlisted party into the freed seat. A second copy of that rule is how a guest gets promised a seat and never told.
  • Recording a sample tasting. The real path also tags the customer and mirrors into reviews. Half of that from here would be a second door onto one act, with different rules.
  • Reading a taster's own notes back. They are a customer's words and their email is the identifier, which is not what an inventory-reading token covers. You get the aggregate.
  • Creating a tea in the receiving shop on a transfer. A new row needs a cost, a currency and a freight rate, and copying the source shop's is exactly the fault the rest of this week was spent removing.
