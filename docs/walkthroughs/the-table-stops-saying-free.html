The table stops saying free

When a tea was added without a freight rate, the table filled in 0. Without a markup, 2.5. Without a cost, 0. Three answers nobody gave, each one looking like a decision. This removes the fill-ins. It changes no tea that exists today; it changes what the next tea gets when a door forgets to say.

What it changes

Every fix since the freight rule was written corrected the rows, but none could reach the table's own habit of answering a blank with a number, because this database cannot change a default in place.

So nine of the ten ways a tea can enter the shop were still landing ships free, markup 2.5 and, for three of them, cost 0, and the inventory list drew a gold dot on the whole shelf claiming you had pinned every one. Measured against a copy of your catalogue: 223 dots before, none after.

The code half is already on main: all ten doors now say the three fields out loud, so a blank stays blank, the shop rate and the times-three apply, and the inventory list reads a blank as following the shop rate. This migration is the second lock. It removes the fill-ins from the table itself, so a door written next year cannot fall into the same hole.

It changes

What the table answers when a future save leaves freight, markup or cost unsaid: nothing, instead of 0, 2.5 and 0. A blank then reads as blank everywhere.

It leaves alone

Every existing tea, listing, price, rate, index and trigger. Your customers see the same prices tomorrow as today.

What it touches, and what it leaves alone

These are seeded shapes, not your shelf. Each row was built to the shape of a real tea and every value came back identical. On the sandbox copy (340 teas, 220 partner listings) the whole table was fingerprinted before and after, and the two fingerprints match. Only what an empty field turns into for a tea added tomorrow differs.

Partner listings carry the same three fields and were checked the same way: nothing moves. Every index and every trigger on both tables is the same before and after, and every table that points at a tea (article links, sales grants, receipt lines, favourites, ten more) came through byte for byte.

Why it is not the usual rebuild

The textbook way to change a default is to build a new table, copy everything across, and drop the old one. On this database that would have quietly deleted the article-to-tea links and the sales grants and blanked the tea references on receipt proposals and favourites, because the switch that is supposed to pause those cascades is accepted and ignored here. The builder measured that rather than trusting it, and the reviewer measured it again. So the migration rewrites the three columns in place: add a twin with no default, copy the column onto it, drop the original, rename the twin back. Nothing is dropped, so nothing can cascade.

Your check

Add a tea through the Add Product form and leave the freight field empty. In the inventory list its Ship $/kg cell shows the shop rate (about 12.63 today) with no gold dot , and the hover text says it is following the shop rate. This already holds on main; the migration keeps it true for doors nobody has written yet.

Scan the Ship $/kg column. Every row showing 0.00 with a dot should be teaware. On the sandbox copy that is 117 rows, all teaware.

Shop. Any tea on the public shelf shows the same price it showed yesterday. Say go and this pushes behind the code that is already on main. Say hold and nothing continues to land free while it waits, because every door now names the three fields itself.
