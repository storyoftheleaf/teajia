## Orders and payments

- [x] Every way of being owed money ends at the same record — done 2026-08-31. Wholesale wrote two invoices carrying a status the app does not have, no line items and no amount, with the two money columns on the same row contradicting each other, so the ledger, the pay link and the attention list could not see the money at all. They are ordinary priced invoices now, marked fulfilled because receiving is the goods changing hands and unpaid because receiving tea is not paying for it, and receiving is refused outright when a line's currency has no exchange rate rather than invoicing it at par. The events half of that item was wrong and was read off the schema: `event_attendees.payment_status` is dead, nothing in the worker reads or writes it, and event money already runs through ordinary `EVT-` invoices. What is actually true about events is filed separately.

- [x] A sample request is recorded whether or not the tea is in the shop — done 2026-08-31. A line may be a named custom line with no product, the shape converting already produces for a retired tea. The product-id requirement had been doubling as the anti-junk gate on a public write, so the gate is stated properly instead: a custom line must say it is custom, at most 50 lines, a name at most 120 characters, a note at most 2000. Three of those four are tighter than what shipped before.

- [x] An order is not sent while a line sits at no price — done 2026-08-31. Draft to pending is the only path that makes an order a real ask, and it refuses there, naming the lines so the screen asks about them by name. "Send anyway" is one click, because the operator is the one who knows whether a line is meant to be free.

- [x] The pay page says which order the money is for — done 2026-08-31 → Plan: [order-process-handoff.md](plans/archive/order-process-handoff.md). It uses the key the customer already holds rather than a new one: they arrive from their own order page, so the same key one step later reveals nothing new, and a stranger who guesses a reference code still sees exactly what they saw before. The token never enters the address, because this page renders its own address as a QR code and hands it out under a heading inviting the visitor to share it. Four further problems were found and fixed in the same pass: the order body was staying out of durable browser storage only by a lucky substring match, the one line wiring the feature up had no test and deleting it left everything green, the recipient was not checked alongside the shop so a hand-edited link could show a real order above the wrong person's bank details, and the customer's private key was reaching the incident log through a path recorded verbatim. A fifth was found by opening the live page on a phone: the block sized itself to the longest tea name and pushed the amount 208px off a 375px screen, invisible to every test because the page reported no sideways scroll.

- [x] Close the loop from an order request to being paid — done 2026-08-31, live at teajia.com. An order request now reaches Adrian by email instead of waiting to be noticed, becomes a priced invoice in one click instead of being retyped, and carries a pay link resolved to the right tea master with the amount and a reference to quote. Payments got their own records, so a customer can report a transfer and Adrian confirms it against his bank: a report is never money, part payments work, and the pay link asks for the balance outstanding rather than the full amount again. What the customer sees on their tracking page is now derived from the order itself instead of a status kept by hand, which was generating the "where is my tea" messages the page exists to answer. What needs Adrian gathers into one list in Your Table, oldest waiter first, and six voice commands reach all of it. Fixed along the way: the fulfilment email had never sent because it looked for a column that does not exist and pointed at a domain Teajia does not own; marking an order paid the old quick way now leaves a ledger row so history cannot contradict status; sample requests and AI-prepared orders were vanishing into WhatsApp unrecorded; the cart survived checkout so an order could be sent twice; and the baseline schema carried a Cloudflare internal table that made a fresh database fail to build. Three rounds, ten agents. Remaining work is in [order-process-handoff.md](plans/order-process-handoff.md), which stays live. → Plans: [order-process.md](plans/archive/order-process.md), [round two](plans/archive/order-process-round-2.md), [round three](plans/archive/order-process-round-3.md), [cross-agent notes](plans/archive/order-process-notes.md)

- [x] Stop writing the payment ledger rules twice — done 2026-08-31. Eleven pieces of the money code had been copied from `worker/src/index.ts` into `worker/src/mcp.ts` under a "keep in sync" note, because index imports mcp and the reverse would close a module cycle, so a change to what counts as paid had to be made in both files. They now live in `worker/src/invoiceDomain.ts`, which imports neither, and both import from it: PAYMENT_EPSILON, the text limits and caps, roundUsd, paymentTextField, formatInvoiceNumber, loadInvoiceLedgerTotals, invoiceMoney, loadLedgerInvoice, reconcileLedgerWithColumn, recomputeInvoicePaymentStatus. The same pass closed the one place the two implementations disagreed: `whats_waiting` required `status = 'Draft'` across both halves of its unpriced question, so a Pending order carrying a line priced at nothing was on the screen and not in the spoken answer. `worker/tests/attention-parity.test.ts` now asserts the screen and the voice return the same list, and fails if either drifts.
